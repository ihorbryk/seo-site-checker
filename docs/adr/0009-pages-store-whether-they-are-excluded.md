# Pages store whether an exclude pattern matches them

The MVP spec (#19) and the code said "exclusion is computed, never stored": whether a Page is excluded came from the Project's current exclude patterns on every render. That kept the answer from ever drifting from the patterns, but only Go can match a pattern (the `exclude` package, a glob with its own `*` and `**` rules). So the Page pool tab (#41) read every Page of the Project, classified each in Go, counted the six filters and sliced one page of ids. At 2M Pages that is 2M rows read, sorted and held in memory per request, and again after a Page is added by hand (#71, #77).

Now each Page stores `excluded`: whether one of its Project's current patterns matches it. Go stays the only place a pattern is matched (`page.Excluded`, which never excludes the seed Page); SQL never matches a pattern. The answer is set when a Page is added (URL discovery, by hand, with a new Project). Saving different exclude patterns bumps the Project's `exclude_gen`, resets its `exclude_cursor` and enqueues `ExcludeRecompute`, which recomputes the Pages in batches the way a Check is planned (ADR 0006): a fixed batch by id, the cursor advanced and the next job enqueued in the same transaction, a job that acts only if its `after_page_id` is still the cursor and its generation is still current, so a duplicate, a retry or the chain of an older save does nothing. Its timeout (2 min) is below the stuck-job delay. The tab then counts with one SQL aggregate and lists each filter with its own query, ordered by URL and paginated, served by one partial index per filter. `poolState` still labels a Page, and a test pins every SQL filter to it over all combinations of state, origin, orphan streak and match.

Planning and URL discovery are unchanged: they match patterns in Go against the settings frozen onto the Check (ADR 0006), not the stored answer.

## Ordering and races

- A Page inserted while patterns are being saved must not keep an answer from the old patterns. Every insert reads the Project's patterns with `FOR SHARE` and holds the lock to its commit; saving the patterns and each recompute batch take the Project row `FOR NO KEY UPDATE`. A save therefore waits for inserts that read the old patterns, and later inserts read the new ones. Every Page that exists once the save commits is either already visible to the recompute or has the new answer.
- Saving again while a recompute runs bumps the generation. A batch in flight finishes first (the lock), then the old chain's next job sees the newer generation and stops; the new chain starts at the first Page, so every Page ends with the newest patterns.
- Unfinished work is a durable mark. A Project's recompute is unfinished while `exclude_done_gen < exclude_gen`; the worker sets `exclude_done_gen` when a batch comes back short (the last Page). The scheduler's tick queues the next job, resuming at `exclude_cursor`, for every unfinished Project that has no live `exclude_recompute` job. A discarded job, a job failed by an old worker that does not know the kind, or a lost chain therefore only delays the recompute.
- Pages that exist when this is deployed: the migration marks every Project with exclude patterns as generation 1, done generation 0, and inserts no job. `docker compose up -d` runs the migration while the old worker is still up; a job inserted by the migration could be claimed and failed by it (unknown kind) until River discards it, and the Pages would stay unclassified. The scheduler queues the job once the new code runs. A Project with no patterns is already right (default `false`).
- Saving patterns and adding Pages: a lane step that discovers Pages takes the Project row `FOR SHARE`, which waits behind a recompute batch holding `FOR NO KEY UPDATE` for the whole batch (median 0.23 s, longest 1.1 s at 20,000 Pages). A Fetch whose step finds new links can therefore wait up to a second; the lane's other steps do not take the lock. This is accepted: shrinking the batch would multiply the jobs, and a wait of that size is small against a Fetch's own timeout.

## Considered Options

- **Match patterns in SQL (translate the globs to regular expressions or `LIKE`)**: rejected. A second matcher would have to stay identical to the Go one for `*`, `**`, `?` and query strings, and a difference would show a Page as excluded in the tab and fetch it in the next Check. The same rule in two languages is what the stored answer avoids.
- **Counters on the Project row for the filter counts**: rejected. Every state change, orphan streak update and retire would have to adjust them in the same transaction as many writers (lanes, finalize, ignore, restore), and any miss is permanent drift. One aggregate over the Project's Pages still grows with the pool, but it is cheap (about 120 ms at 2M Pages) and it cannot drift.
- **Keep classifying in Go, cache the result**: rejected. The first request after any change would still read the whole pool, and the cache would need the same invalidation as the stored answer.

## Consequences

- After saving patterns the tab shows each Page's old answer until the job reaches it. There is no "updating" indicator; at 20,000 Pages per job a 2M-Page pool takes about 100 short jobs (median 0.23 s, longest 1.1 s on a laptop).
- The stored answer is never read when a Check is planned, so a Check that starts mid-recompute still uses its own frozen patterns. Using the stored answer there is a separate decision.
- Pages gain five partial indexes (`pages_pool_*_idx`) and `pages_project_id_idx (project_id, id)` for the recompute batches. They are built concurrently in the migration (13.8 s at 2M Pages), which is safe to rerun.
- The seed Page is stored as not excluded whatever the patterns say.
